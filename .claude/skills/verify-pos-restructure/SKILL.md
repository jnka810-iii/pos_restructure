# พิสูจน์พฤติกรรมของ pos_restructure

สคิลนี้ขับ **อินสแตนซ์แยกของแอป** ไม่ใช่แอปที่ผู้ใช้เปิดอยู่ ทุกการตรวจได้ฐานข้อมูล โฟลเดอร์ไฟล์แนบ กุญแจเซสชัน และ log ของตัวเอง ในโฟลเดอร์ใต้ `%TEMP%\pos-verify\` และได้พอร์ตว่างที่สุ่มมา ไม่ใช่พอร์ต 5020 ที่ `run.bat` ใช้ ข้อมูลจริงของหน่วยงานใน `pos_restructure.db` และ `uploads/` จึงไม่ถูกแตะเลย

**พื้นผิวที่ผู้ใช้สัมผัส** คือหน้าเว็บหน้าเดียวที่มีสามแท็บ (กรอกข้อมูล / คำขอทั้งหมด / สรุปภาพรวม) เปิดได้สามทางคือหน้าต่าง pywebview (`run.bat`) เบราว์เซอร์ปกติ (`run_browser.bat`) และเครื่องอื่นในวง LAN (`run_server.bat`) สคิลนี้ขับทางเบราว์เซอร์ ซึ่งเป็นหน้าเว็บชุดเดียวกับที่ pywebview แสดง ส่วน `.exe` ที่ build ด้วย pyinstaller และหน้าต่าง pywebview เอง สคิลนี้ขับไม่ได้ ดูหัวข้อ [ที่สคิลนี้พิสูจน์ไม่ได้](#ที่สคิลนี้พิสูจน์ไม่ได้)

คำสั่งทั้งหมดมาจากตัวเดียวคือ `control_pos.py` ทุกคำสั่งพิมพ์ JSON หนึ่งก้อนและคืน exit code 0 เมื่อสำเร็จ

## ตัวช่วยที่สคิลนี้มี

| ไฟล์ | หน้าที่ |
| --- | --- |
| `control_pos.py` | คำสั่งเดียวที่ใช้ขับทุกอย่าง แบ่งเป็นหมวด `app` `doctor` `api` `browser` `users` `data` |
| `cdp.py` | ตัวขับเบราว์เซอร์ผ่าน Chrome DevTools Protocol เขียนด้วยไลบรารีมาตรฐานล้วน ไม่ต้องลง Playwright หรือ Selenium และไม่แตะ `requirements.txt` |
| `features/` | แผนที่ความสามารถที่ผู้ใช้ใช้จริง หนึ่งไฟล์ต่อหนึ่งความสามารถ อ่าน [`features/README.md`](features/README.md) ก่อนลงมือขับ |

วิธีเรียก ตั้งตัวแปรนี้ไว้ก่อนแล้วใช้ `$POS` นำหน้าทุกคำสั่งในเอกสารนี้

```bat
REM จาก root ของโปรเจกต์ (cmd หรือ PowerShell)
set POS=.venv\Scripts\python.exe .claude\skills\verify-pos-restructure\control_pos.py
%POS% --help
```

```bash
# Git Bash
POS=".venv/Scripts/python.exe .claude/skills/verify-pos-restructure/control_pos.py"
$POS --help
```

ทุกคำสั่งและทุกหมวดมี `--help` ที่บอกความหมายของแต่ละตัวเลือกไว้ครบ เมื่อไม่แน่ใจให้อ่าน `--help` ของคำสั่งนั้นก่อนเดา

## Launch — เปิดอินสแตนซ์

```bash
$POS app start            # โหมดเครื่องแม่ข่าย ใช้ได้กับเกือบทุกอย่าง
$POS app start --lan      # โหมดเดียวกับ run_server.bat ทุกคนต้องเข้าสู่ระบบ
```

คำสั่งนี้ทำครบในครั้งเดียวจากสภาพว่างเปล่า

1. สุ่มพอร์ตว่าง สร้าง `run_dir` ใหม่ แล้วเปิด Flask ด้วยโฟลเดอร์ข้อมูลของตัวเอง `init_db()` สร้างตารางและ migrate timestamp ให้เองตอนเริ่ม ไม่ต้องรัน migration แยก
2. รอจน **ใช้งานได้จริง** ไม่ใช่แค่พอร์ตเปิด เงื่อนไขของโหมดปกติคือ `/api/ping` ตอบ `ok` **และ** `/api/positions` ตอบเป็นรายการ **และ** ตาราง `positions` กับ `users` ถูกสร้างครบในไฟล์ฐานข้อมูล ส่วนโหมด `--lan` คือ `/api/ping` ตอบ `401` **และ** `/login` แสดงฟอร์มแล้ว **และ** ตารางถูกสร้างครบ เพราะ 401 ในโหมดนั้นแปลว่าด่านทำงานอยู่ ไม่ใช่แปลว่ายังไม่พร้อม พอร์ตเปิดก่อนที่ `init_db()` จะเสร็จได้ การเชื่อว่าพอร์ตเปิดเท่ากับพร้อมจึงทำให้คำสั่งถัดไปล้มแบบอธิบายไม่ถูก
3. ใส่คำขอตั้งต้นสองใบ (สถานะ `อนุมัติ` กับ `อยู่ระหว่างพิจารณา` มีค่าตอบแทนและข้อมูลส่วนที่ 1 ถึง 3 ครบ) ข้ามด้วย `--no-seed` ถ้าต้องการเริ่มจากฐานข้อมูลว่างจริงๆ
4. เปิด Edge หรือ Chrome แบบ headless ที่เปิดพอร์ต CDP ไว้ แล้วจดเลข target ของหน้าหลักไว้ หน้านั้นอยู่ค้างระหว่างคำสั่ง จึงขับต่อกันหลายคำสั่งในหน้าเดียวได้

`--lan` เรียก `app.serve(host='0.0.0.0')` ตัวเดียวกับที่ `run_server.bat` เรียก ซึ่งบังคับเข้าสู่ระบบกับทุกคนรวมถึง `127.0.0.1` และปฏิเสธที่จะเปิดเมื่อยังไม่มีบัญชีสักคน สคิลจึงสร้างบัญชี `verify` รหัสผ่าน `verify-pass-1` ไว้ให้ก่อนเปิดเซิร์ฟเวอร์ และรายงานไว้ใน `lan_account` ใช้บัญชีนี้ทุกครั้งที่ต้องเข้าสู่ระบบ ไม่ว่าจะจาก `--from local` หรือ `--from lan`

ผลลัพธ์บอก `base_url`, `lan_url`, `run_dir`, `evidence_dir`, `git_commit` และ id ของคำขอที่ใส่ไว้ คำสั่งถัดๆ ไปไม่ต้องส่ง `--run-dir` เพราะอินสแตนซ์ล่าสุดถูกจดไว้ที่ `%TEMP%\pos-verify\current.json` ให้แล้ว

**ขับได้ครั้งละหนึ่งอินสแตนซ์** `app start` ปฏิเสธถ้ายังมีตัวที่เปิดอยู่ ให้ `app stop` ก่อน การเปิดทับทำให้ตัวเก่าค้างโดยไม่มีใครรู้ว่าต้องปิดอย่างไร ถ้าต้องการสองตัวพร้อมกันจริงๆ ให้ระบุ `--run-dir` ที่ต่างกันทั้งคู่ แต่ละตัวได้พอร์ตและโฟลเดอร์ข้อมูลของตัวเองอยู่แล้ว

## Doctor — ตรวจก่อนขับ

```bash
$POS doctor
```

อ่านอย่างเดียว ไม่แก้อะไร คืน exit code 1 เมื่อมีข้อไม่ผ่าน และรันเป็นอย่างแรกทุกครั้งที่มีอะไรดูผิดปกติ ตรวจ 8 ข้อ

- เซิร์ฟเวอร์ยังทำงานอยู่ และเลข pid ที่จดไว้ยังเป็น `python.exe` จริง
- **พอร์ตนี้เป็นของอินสแตนซ์ที่เปิดไว้เอง** เทียบ pid ที่ถือพอร์ตกับที่จดไว้ บน Windows แอปหลายตัวเปิดพอร์ตเดียวกันได้ ข้อนี้คือสิ่งที่กันการขับตัวอื่นโดยเข้าใจผิด
- `/api/ping` ตอบ `ok` ในโหมดปกติ
- หน้าเว็บคือแอปตัวนี้ และเลขเวอร์ชันที่ footer ตรงกับ `APP_VERSION` ใน `app.py`
- ฐานข้อมูลที่ขับอยู่เป็นของการตรวจ ไม่ใช่ `pos_restructure.db` ของโปรเจกต์
- เบราว์เซอร์ที่ใช้ขับยังทำงานอยู่ และหน้าหลักที่จดไว้ยังเปิดอยู่
- เมื่อเปิดด้วย `--lan` เส้นทางของเครื่องในวงต้องตอบ 401 ตราบที่ยังไม่เข้าสู่ระบบ และ `127.0.0.1` ต้องตอบ 401 ด้วยเหมือนกัน เพราะโหมดนี้ไม่ยกเว้นให้ใคร ข้อตรวจเลขเวอร์ชันจึงอ่านจาก `/login` แทน `/` ในโหมดนี้

## Drive — ขับแอป

### หน้าเว็บ

```bash
$POS browser open                               # เปิด / และรอจนป้ายสถานะขึ้น "เชื่อมต่อแล้ว"
$POS browser open --path login --from lan       # เปิดในบทบาทเครื่องในวง
$POS browser click --text "คำขอทั้งหมด"
$POS browser click --select '#confirmOk'
$POS browser fill --select '#p4_status' --value "อนุมัติ"
$POS browser attach --select '#file_attach' --sample pdf
$POS browser press --key Enter --select '#search-input'
$POS browser read --table '#tbl' --wait-text "777"
$POS browser shot --name save-request --with-text
```

ตัวระบุองค์ประกอบมีสองแบบ ใช้ `--select` (CSS) กับช่องกรอกที่มี id หรือ name และใช้ `--text` (ข้อความที่ผู้ใช้เห็น) กับปุ่ม ลิงก์ และแท็บ `--text` เทียบแบบตรงตัวก่อน ถ้าไม่เจอจึงลองขึ้นต้นด้วย แล้วจึงมีคำนี้อยู่ และบอกกลับมาว่าใช้วิธีไหน เมื่อตรงหลายรายการให้เลือกด้วย `--nth`

คลิกและพิมพ์ส่งผ่าน `Input.dispatchMouseEvent` และ `Input.insertText` ซึ่งเป็น event ที่เบราว์เซอร์สร้างให้เหมือนคนทำจริง ไม่ใช่การเรียก `element.click()` จาก JavaScript ก่อนคลิกทุกครั้ง ตำแหน่งขององค์ประกอบจะถูกวัดซ้ำจนค่าหยุดนิ่งและอยู่ในกรอบที่มองเห็น การคลิกตามตำแหน่งที่วัดพร้อมคำสั่งเลื่อนจอจะไปลงที่ว่างนอกจอ ซึ่งไม่เกิดอะไรขึ้นเลยและอ่านจากผลไม่ออกว่าพลาดเพราะอะไร

ทุกคำสั่งรายงาน `method` ที่ใช้จริง ข้อยกเว้นสองอย่างที่ไม่ใช่การกดจริงคือ `<select>` กับ `<input type="date">` ซึ่งรายงานเป็น `set-value+events` เพราะหน้าต่างเลือกของสองอย่างนี้เป็น UI ของระบบปฏิบัติการ ไม่ได้อยู่ในหน้าเว็บ และช่องแนบไฟล์ซึ่งรายงานเป็น `DOM.setFileInputFiles` ซึ่งเป็นสิ่งที่เบราว์เซอร์ทำหลังผู้ใช้เลือกไฟล์ในหน้าต่างของระบบ ทั้งสามกรณียังผ่าน event handler จริงของหน้าเว็บทุกตัว

`browser read` คืนที่อยู่ ชื่อหน้า ป้ายสถานะ ชื่อผู้ใช้งาน ตัวเลขจำนวนคำขอ แท็บที่เปิดอยู่ ข้อความแจ้งเตือน สรุปข้อผิดพลาด กล่องที่เปิดอยู่ ข้อความ และปุ่มที่กดได้ ใส่ `--table` เพื่อแปลงตารางเป็นแถวและคอลัมน์ และ `--wait-text` เพื่อรอให้ข้อความหนึ่งปรากฏ ซึ่งเชื่อถือได้กว่าการนอนรอตามเวลา

### API

```bash
$POS api GET api/positions
$POS api POST api/positions --data @payload.json
$POS api DELETE api/positions/3 --dry-run       # ดูคำขอที่จะส่งก่อน
$POS api GET api/positions --from lan --fresh   # คาดว่าได้ 401
$POS api GET api/positions --from lan --login somchai:verify-pass-1
```

`--from local` คือคำขอจาก `127.0.0.1` ซึ่งไม่ต้องเข้าสู่ระบบในโหมดปกติ แต่ต้องเข้าสู่ระบบในโหมด `--lan` เหมือนทุกคน `--from lan` เรียกผ่าน IP ของเครื่องนี้ ทำให้ `request.remote_addr` ไม่ใช่ loopback แอปจึงนับเป็นเครื่องในวงจริงๆ โดยข้อมูลไม่ได้ออกไปนอกเครื่อง คุกกี้เซสชันเก็บเป็นไฟล์ใน `run_dir` คำสั่งหลายคำสั่งจึงอยู่ในเซสชันเดียวกันได้

### บัญชีผู้ใช้งานและข้อมูล

```bash
$POS users add --username somchai --display "สมชาย ใจดี" --password verify-pass-1
$POS users list
$POS data seed                      # ทำซ้ำได้ ไม่เกิดคำขอซ้ำ
$POS data reset                     # dry-run ก่อน
$POS data reset --apply
```

`manage_users.py` ของโปรเจกต์ถามรหัสผ่านทางแป้นพิมพ์ซึ่งขับอัตโนมัติไม่ได้ `users add` จึงใช้กติกาเดียวกัน (ชื่อผู้ใช้งาน `a-z 0-9 . _ -` ยาว 3 ถึง 32 ตัว รหัสผ่านอย่างน้อย 8 ตัว เก็บเป็นแฮช) แต่รับรหัสผ่านมาเป็นอาร์กิวเมนต์ คำสั่งหมวดนี้แก้ได้เฉพาะฐานข้อมูลที่อยู่ใน `run_dir` ถ้าเส้นทางหลุดออกไปข้างนอก คำสั่งจะปฏิเสธ บัญชีจริงของหน่วยงานยังจัดการด้วย `manage_users.py` เท่านั้น

### คำสั่งที่ลบหรือแก้ข้อมูล

ทุกคำสั่งที่เปลี่ยนข้อมูลรับ `--dry-run` ซึ่งแสดงสิ่งที่จะทำโดยไม่ทำ สองคำสั่งที่ย้อนกลับไม่ได้คือ `data reset` และ `users remove` เป็น dry-run โดยค่าเริ่มต้นและต้องใส่ `--apply` จึงจะทำจริง แบบเดียวกับ `cleanup_orphans.py` และ `migrate_schema.py` ของโปรเจกต์ `app stop` รับ `--dry-run` เพื่อดูว่าจะปิด pid ไหนและลบโฟลเดอร์ไหน

อย่าเชื่อชื่อ `--dry-run` อย่างเดียว ผลที่คืนมาบอกว่าจะลบอะไรกี่รายการและไฟล์ชื่ออะไร ให้อ่านรายการนั้นเทียบกับที่คาดก่อนสั่ง `--apply`

## Evidence — หลักฐาน

`browser shot --name <ชื่อ>` เขียน `<evidence_dir>/<ชื่อ>.png` และเมื่อใส่ `--with-text` จะเขียน `<ชื่อ>.json` ที่เป็นข้อความ ป้ายสถานะ ตัวเลขจำนวนคำขอ และตารางของหน้านั้นคู่กันไปด้วย ไฟล์ภาพพิสูจน์ว่าหน้าตาเป็นอย่างไร ไฟล์ JSON พิสูจน์ว่าข้อความข้างในเป็นอะไรแน่โดยไม่ต้องอ่านจากภาพ `evidence_dir` อยู่ใน `run_dir` และ **ไม่ถูกลบตอน `app stop`**

เกณฑ์ของหลักฐานที่ใช้ได้

- ขับทางที่ผู้ใช้ใช้จริง ห้ามพิสูจน์การบันทึกด้วยการยิง `POST /api/positions` แล้วบอกว่าฟอร์มทำงาน ฟอร์มมี `validateRequest` ของตัวเองที่ API ไม่มี
- เก็บทั้งการลงมือและสภาพที่เกิดขึ้นตามมา ไม่ใช่เฉพาะหน้าจอสุดท้าย ข้อความ `บันทึกคำขอเรียบร้อยแล้ว` อย่างเดียวไม่พอ ต้องกลับไปดูในแท็บคำขอทั้งหมดว่ามีคำขอใบนั้นจริง
- พิสูจน์ผลข้างเคียงด้วย ไม่ใช่แค่ที่ตาเห็น คำขอที่บันทึกแล้วต้องเห็นจาก `api GET api/positions` และไฟล์แนบต้องมีอยู่จริงในโฟลเดอร์ `uploads` ของอินสแตนซ์
- ไม่ mock อะไรเลย แอปนี้ไม่เรียกบริการภายนอก ไลบรารีหน้าเว็บทั้งหมดอยู่ใน `static/vendor` ถ้าต้องตรวจว่าใช้งานออฟไลน์ได้ ให้ใช้ `verify_offline.py` ของโปรเจกต์ซึ่งทำเรื่องนั้นอยู่แล้ว
- บันทึกว่าพิสูจน์ความสามารถไหนด้วยทางเข้าไหน ความสามารถหนึ่งมีหลายทางเข้า การพิสูจน์ทางเดียวแล้วบอกว่าครบทั้งความสามารถคือรายงานเกินจริง

เมื่อเส้นทางหนึ่งขับไม่ได้ ให้รายงานว่าล้มเหลวพร้อมคำสั่งที่ใช้และเงื่อนไขที่ยังไม่ครบ แล้วบันทึกเหตุไว้ใน `Gotchas` ของไฟล์ความสามารถนั้น **ห้ามลดความเข้มของเส้นทางเพื่อให้ผ่าน**

## Cleanup — เก็บของ

```bash
$POS app stop --dry-run     # ดูก่อนว่าจะปิดอะไร
$POS app stop
```

ปิดเฉพาะโปรเซสที่การตรวจครั้งนี้เปิดเองตามเลข pid ที่จดไว้ และตรวจชื่อ executable ก่อนฆ่าทุกครั้ง เพราะ Windows เอาเลข pid กลับมาใช้ซ้ำได้ **ห้ามปิดตามชื่อโปรเซส** และห้ามใช้ `stop_app.ps1` ของโปรเจกต์ในการเก็บของหลังตรวจ เพราะมันปิดทุกตัวที่ถือพอร์ต 5020 ซึ่งคือแอปที่ผู้ใช้เปิดอยู่

`app stop` ลบ `browser-profile` กับ `scaffolding` (ไฟล์ตัวอย่างที่ `browser attach --sample` สร้าง) และ **เก็บ** `evidence/` `data/` `server.log` `state.json` ไว้ ถ้าเบราว์เซอร์ยังปล่อยไฟล์ไม่เสร็จ ผลลัพธ์จะบอกใน `left_behind` ว่าโฟลเดอร์ไหนลบไม่หมด ซึ่งไม่กระทบหลักฐาน

`run_dir` ของการตรวจเก่าสะสมอยู่ใต้ `%TEMP%\pos-verify\` ลบด้วยมือเมื่อไม่ต้องการหลักฐานชุดนั้นแล้ว

เมื่อรอบที่ล้มเหลวทำให้คำสั่งค้าง ให้รัน `app stop` เหมือนกัน รอบที่พังจึงไม่ทิ้งโปรเซสและพอร์ตค้างไว้

## กับดักที่ทำให้เสียเวลาหรือได้ผลที่เชื่อไม่ได้

- **Git Bash แปลงเส้นทางให้เอง** `--path /login` มาถึงโปรแกรมเป็น `C:/Program Files/Git/login` คำสั่งจับกรณีนี้ได้และบอกวิธีแก้ ให้เขียนแบบไม่มี `/` นำหน้า เช่น `--path login` และ `api GET api/positions` ซึ่งใช้ได้กับทุกเชลล์
- **คุกกี้ค้างทำให้เส้นทาง 401 หายไป** คุกกี้เซสชันถูกเก็บไว้ใช้ต่อ หลังเข้าสู่ระบบแล้วคำสั่งถัดไปจะไม่ได้ 401 อีก การพิสูจน์ว่าเครื่องในวงที่ยังไม่เข้าสู่ระบบถูกปฏิเสธ ต้องใส่ `--fresh`
- **การเข้าสู่ระบบที่ผิดใช้เวลาหนึ่งวินาที** `app.py` หน่วงไว้หนึ่งวินาทีเมื่อรหัสผ่านผิด แล้วหน้าเว็บล้างช่องรหัสผ่านทิ้งหลังจากนั้น ถ้าพิมพ์รหัสใหม่ทันทีจะถูกล้างทับ ให้รอข้อความผิดพลาดด้วย `browser read --select '#login-error' --wait-text "ไม่ถูกต้อง"` ก่อนพิมพ์ใหม่
- **ช่องแนบไฟล์ถูกซ่อนไว้** `#file_attach` เป็น `display:none` และตัวที่ผู้ใช้เห็นคือ `#upload-zone` การคลิก `#upload-zone` จะเปิดหน้าต่างเลือกไฟล์ของระบบ ซึ่งขับไม่ได้และอาจค้าง ให้ใช้ `browser attach` ที่ป้อนไฟล์ให้ช่องที่ซ่อนอยู่โดยตรง
- **หน้าต่างพิมพ์ PDF เป็นอีกหน้าหนึ่ง** `ดูตัวอย่าง / พิมพ์ PDF` เปิดหน้าใหม่ด้วย `window.open` อ่านและถ่ายภาพด้วย `--window latest` และปิดด้วย `browser read --window latest --expr "window.close()"` ถ้าไม่ปิด `--window latest` จะยังชี้ไปที่หน้านั้นอยู่
- **ข้อความที่ซ่อนอยู่อ่านด้วย innerText ไม่ได้** `#toast-msg` และ `#form-errors` ถูกซ่อนไว้ตอนไม่ใช้ `browser read` กับ `click` จึงคืนทั้งข้อความและสถานะว่าตอนนี้แสดงอยู่หรือไม่ ให้ดู `shown` ไม่ใช่ดูแค่ว่ามีข้อความ
- **โหมด `--lan` ขอรหัสผ่านจาก `127.0.0.1` ด้วย** ผลที่ตามมาคือ `data seed` กับ `data reset` เข้าสู่ระบบเป็น `verify` ให้เองก่อนเขียนข้อมูล และ `api ... --fresh` จากเครื่องแม่ข่ายจะได้ 401 ซึ่งถูกต้องแล้ว ไม่ใช่อินสแตนซ์พัง
- **`--lan` เปิดพอร์ตกับทั้งวง** โหมดนี้ bind `0.0.0.0` บนพอร์ตสุ่ม Windows Firewall ปิดขาเข้าไว้โดยค่าเริ่มต้นจึงไม่มีเครื่องอื่นต่อเข้ามาได้ แต่ถ้าเครื่องนั้นเปิดพอร์ตกว้างไว้ ให้ใช้โหมดปกติแทนและข้ามเส้นทางของเครื่องในวงไป พร้อมรายงานว่าข้ามเพราะอะไร
- **การ import `app.py` เปิดไฟล์ log ของโปรเจกต์** `app.py` ผูก log handler ไปที่ `<repo>\pos_restructure.log` ตอน import สคิลย้าย handler มาที่โฟลเดอร์ของการตรวจทันทีหลัง import แต่ไฟล์ของโปรเจกต์ถูกเปิดเพื่อเขียนต่อท้ายไปแล้วหนึ่งครั้ง (ถูกสร้างขึ้นถ้ายังไม่มี) ไฟล์นี้อยู่ใน `.gitignore` และไม่มีอะไรถูกเขียนลงไป
- **`p4_date` และ `p4_effective` เก็บเป็น ค.ศ.** ช่องวันที่เป็น `<input type="date">` ค่าที่ส่งคือ `YYYY-MM-DD` แบบ ค.ศ. หน้าเว็บแปลงเป็น พ.ศ. ตอนแสดงผล ให้ assert ค่าที่แสดงบนหน้า ไม่ใช่ค่าที่กรอกเข้าไป

## ที่สคิลนี้พิสูจน์ไม่ได้

ที่ตรวจไว้แล้วบนเครื่องนี้คือหน้าเว็บที่เสิร์ฟจาก `app.py` ผ่าน Edge headless สิ่งต่อไปนี้ยังไม่มีหลักฐานและต้องตรวจด้วยมือ

- **หน้าต่าง pywebview** (`run.bat`) ขับไม่ได้ เพราะ WebView2 ไม่ได้เปิดพอร์ต CDP ให้ หน้าเว็บที่อยู่ข้างในเป็นไฟล์ชุดเดียวกับที่สคิลนี้ขับ แต่ตัวหน้าต่าง ขนาดเริ่มต้น และ `wait_for_port` ก่อนเปิดหน้าต่าง ยังไม่ถูกพิสูจน์
- **`.exe` ที่ build ด้วย pyinstaller** ไม่ถูกแตะเลย ข้อที่ `--add-data "static;static"` หลุดไปแล้วแท็บสรุปภาพรวมพัง ต้องตรวจจากไฟล์ที่ build จริง
- **เครื่องอื่นในวง LAN จริงๆ** สคิลจำลองบทบาทเครื่องในวงด้วยการต่อกลับมาที่ IP ของเครื่องตัวเอง ซึ่งพิสูจน์ด่าน `require_login` กับ `from_this_machine()` ได้ตรงตามโค้ด แต่กฎ Windows Firewall ที่ `run_server.bat` เพิ่มให้ `remoteip=localsubnet` และคำเตือนเรื่องสายแลนไม่ได้เสียบ ยังไม่ถูกพิสูจน์
- **การพิมพ์ออกกระดาษหรือบันทึกเป็น PDF จริง** สคิลพิสูจน์ได้ว่าหน้าตัวอย่างถูกสร้างและมีเนื้อหาอะไร แต่ปุ่ม `window.print()` เปิดกล่องพิมพ์ของระบบ ซึ่งขับไม่ได้
- **การลากไฟล์มาวาง** (`handleDrop`) ขับไม่ได้ ทางที่พิสูจน์ได้คือการเลือกไฟล์ผ่านช่องแนบไฟล์
