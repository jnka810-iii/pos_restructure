# แผนที่ความสามารถของ pos_restructure

โฟลเดอร์นี้เป็นแหล่งอ้างอิงที่ดูแลไว้สำหรับพิสูจน์พฤติกรรมที่ผู้ใช้เห็น อ่านดัชนีนี้ก่อนลงมือขับ แล้วใช้ไฟล์ของความสามารถนั้นเป็นสูตร

## สภาพตั้งต้น

- เปิดอินสแตนซ์ด้วย `$POS app start` ซึ่งได้พอร์ตว่างที่สุ่มมาและโฟลเดอร์ข้อมูลของตัวเองใต้ `%TEMP%\pos-verify\` ไม่ใช่พอร์ต 5020 และไม่ใช่ข้อมูลจริง
- ใช้ `$POS app start --lan` เมื่อจะพิสูจน์เส้นทางของเครื่องในวง LAN โหมดนั้นเรียก `app.serve(host='0.0.0.0')` ตัวเดียวกับ `run_server.bat` จึงบังคับเข้าสู่ระบบกับทุกคนรวมถึง `127.0.0.1` และสคิลสร้างบัญชี `verify` รหัสผ่าน `verify-pass-1` ไว้ให้ก่อนเปิดเซิร์ฟเวอร์
- คำขอตั้งต้นสองใบถูกใส่ให้แล้ว ใบที่หนึ่งสถานะ `อนุมัติ` ตำแหน่งเลขที่ `001` ประเภท `วิชาการ` ระดับ `ชำนาญการพิเศษ` กอง `กองการเจ้าหน้าที่` ค่าตอบแทน `45000.50` ใบที่สองสถานะ `อยู่ระหว่างพิจารณา` ตำแหน่งเลขที่ `002` ประเภท `ทั่วไป` ระดับ `อาวุโส` กอง `กองคลัง` ทั้งสองใบมี `p4_note` เป็น `ชุดตรวจ verify-pos-restructure`
- ตั้ง `POS` ให้ชี้ไปที่ `control_pos.py` ตามที่ [`../SKILL.md`](../SKILL.md) บอก
- รัน `$POS doctor` และต้องผ่านทั้ง 8 ข้อก่อนเชื่อผลการขับใดๆ
- ห้ามขับอินสแตนซ์ที่การตรวจครั้งนี้ไม่ได้เปิดเอง

## ข้อตกลงในการขับ

- เริ่มทุกสูตรจากสภาพตั้งต้น เว้นแต่สูตรนั้นระบุเงื่อนไขของตัวเองไว้
- ใช้ `--text` กับปุ่ม ลิงก์ และแท็บ ใช้ `--select` กับช่องกรอกที่มี id หรือ name อย่าอ้างอิงลำดับการกด Tab หรือพิกัดบนจอ
- ถือทุกคำสั่งตามตัวอักษร ชื่อในเครื่องหมายคำพูดและชื่อตัวเลือกห้ามเปลี่ยน
- รอด้วย `--wait-text` ไม่ใช่นอนรอตามเวลา ตารางและกราฟวาดใหม่หลังโหลดข้อมูลเสร็จ
- คืนสภาพข้อมูลหลังทำสิ่งที่เปลี่ยนข้อมูล ด้วย `$POS data reset --apply` แล้ว `$POS data seed` และห้ามลบไฟล์หลักฐานตอนเก็บของ

## การรายงานหลักฐานและสิ่งที่ข้าม

- เก็บทั้งการลงมือและสภาพที่เกิดขึ้นตามมา ไม่ใช่เฉพาะหน้าจอสุดท้าย
- หลักฐานของหน้าเว็บคือ `browser shot --name <ชื่อ> --with-text` ซึ่งได้ทั้งภาพและข้อความของหน้านั้น
- หลักฐานของ API คือคำสั่ง สถานะที่ได้ และเนื้อคำตอบ ซึ่ง `$POS api` คืนมาครบในก้อนเดียว
- หลักฐานของสิ่งที่เปลี่ยนข้อมูล ต้องมีการอ่านซ้ำจากอีกมุมหนึ่งที่ผู้ใช้เห็นได้ เช่น บันทึกจากฟอร์มแล้วไปดูในแท็บคำขอทั้งหมด
- ระบุรหัสความสามารถและทางเข้าที่ใช้กับหลักฐานทุกชิ้น
- เส้นทางที่ขับไม่ได้ให้รายงานพร้อมคำสั่งที่ลองและเงื่อนไขที่ยังไม่ครบ
- ห้ามรายงานทางเข้าที่ข้ามไปว่าพิสูจน์แล้วผ่านทางอื่น

## รูปของไฟล์ความสามารถ

แต่ละไฟล์เริ่มด้วย H1 และหนึ่งย่อหน้าที่อธิบายพฤติกรรมที่ผู้ใช้เห็น แล้วใช้ H2 สี่หัวข้อตามลำดับนี้

1. `Sub-features` รายการรหัสสั้นพร้อมคำอธิบายบรรทัดเดียวต่อหนึ่งพฤติกรรม
2. `How to get to it (user POV)` ทางเข้าทุกทางที่ผู้ใช้ใช้ได้
3. `Driving it with control_pos.py` เริ่มด้วย `Preconditions:` แล้วเป็นหัวข้อย่อยที่จับคู่การลงมือของผู้ใช้กับคำสั่งจริงและผลที่สังเกตได้
4. `Gotchas` กับดักที่ทำให้เสียเวลาหรือทำให้ผลการตรวจเชื่อไม่ได้

เก็บรายละเอียดการทำงานภายในออกไปจากแผนที่ ระบุเฉพาะทางที่ผู้ใช้ใช้ ตัวระบุที่มั่นคง สภาพที่ต้องมีก่อน คำสั่ง และหลักฐานที่สังเกตได้

## ความสามารถ

- [บันทึกคำขอ](./save-request.md) ครอบการกรอกแบบ บอ.1 การตรวจช่องที่จำเป็น การบันทึก การแก้ไขคำขอเดิม การล้างฟอร์ม และหน้าตัวอย่างสำหรับพิมพ์
- [แท็บคำขอทั้งหมด](./request-list.md) ครอบตาราง การค้นหา การกรองตามสถานะ การลบทีละใบ การลบทั้งหมด และการส่งออก CSV กับ JSON
- [แท็บสรุปภาพรวม](./dashboard.md) ครอบการ์ดสถิติและกราฟสี่รูป ซึ่ง `test_api.py` ครอบไม่ถึง
- [เอกสารแนบ](./attachment.md) ครอบการแนบไฟล์ การปฏิเสธชนิดที่ไม่รองรับ การเปิดไฟล์ การเปลี่ยนไฟล์ และการลบไฟล์พร้อมคำขอ
- [การเข้าสู่ระบบของเครื่องในวง LAN](./lan-login.md) ครอบด่าน 401 หน้าเข้าสู่ระบบ รหัสผ่านผิด ชื่อผู้บันทึก และการปฏิเสธลบทั้งหมดจากเครื่องในวง
